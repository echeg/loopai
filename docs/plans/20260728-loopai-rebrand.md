# Ребрендинг в loopai и удаление ненужного функционала

## Overview

Отделить личный форк от апстримного ralphex: переименовать всё, что видит пользователь, в `loopai`,
и удалить функциональность, которая в этом форке не нужна — Docker-обёртку (вместе с AWS Bedrock,
работающим только через неё), поддержку Mercurial, инфраструктуру релизов апстрима и сайт документации.

Проблема: сейчас форк называется ralphex, ставит бинарь `ralphex`, читает `~/.config/ralphex/` и создаёт
`.ralphex/` в каждом проекте. Если рядом стоит апстримный ralphex, оба топчут одни и те же конфиги и
progress-логи. Плюс в репозитории лежит ~6300 строк кода и инфраструктуры, которые здесь никогда
не будут использованы.

**Главное ограничение, определяющее весь дизайн: `module github.com/umputun/ralphex` НЕ меняется.**
Смена module path переписала бы строку импорта в каждом из 78 Go-файлов, и любой последующий
`git merge upstream/master` давал бы текстовый конфликт практически в каждом тронутом апстримом файле.
Форк должен оставаться мержабельным. По той же причине не трогаются сигналы `<<<RALPHEX:...>>>`
(198 вхождений в Go-константах и embedded-промптах) и внутренние имена пакетов.

Итог: снаружи — полноценный `loopai`, внутри — код, который всё ещё можно синхронизировать с апстримом.

`.github/workflows/ci.yml` и `e2e.yml` остаются (тесты и линт). `assets/claude/` остаётся: это
исходники слэш-команд, и они полезны сами по себе; установленный в системе плагин лежит в

**Что НЕ удаляется (решено явно):** веб-дашборд `pkg/web/` + `e2e/`, уведомления `pkg/notify/`,
обёртки альтернативных провайдеров `scripts/*-as-claude/` и `scripts/opencode/`.

**Миграция конфига — чистый разрыв.** `loopai` читает только `~/.config/loopai/` и `.loopai/`.
Старый каталог не читается и не удаляется; при первом запуске ставятся закомментированные дефолты.
Кода миграции не пишем.

**Паттерны проекта:** table-driven тесты с testify, `t.Helper()` в хелперах, `t.TempDir()` для файловых
операций, комментарии строчными буквами, один `_test.go` на файл исходника.

**Правило проекта:** `CHANGELOG.md` во время разработки не трогать — он часть релизного процесса.

## Development Approach

- **Testing approach**: обычный. Работа состоит из удаления и переименования; новых функций нет,
  поэтому тесты не пишутся с нуля, а обновляются вслед за кодом.
- Выполнять каждую задачу полностью перед переходом к следующей
- Небольшие сфокусированные изменения
- **CRITICAL: каждая задача ОБЯЗАНА содержать новые/обновлённые тесты** для своих изменений кода
  - для задач удаления это означает: удалить осиротевшие тесты и убедиться, что остальные проходят
  - для задач переименования: обновить все захардкоженные пути и строки в тестах и testdata
  - покрытие успешных и ошибочных сценариев сохраняется на прежнем уровне
- **CRITICAL: все тесты должны проходить до начала следующей задачи** — без исключений
- **CRITICAL: обновлять этот файл плана при изменении объёма работ**
- Запускать тесты после каждого изменения
- **Обратная совместимость с ralphex НЕ сохраняется намеренно** — это разрыв, а не миграция.
  Совместимость сохраняется только с апстримом на уровне слияния кода: module path, сигналы
  `<<<RALPHEX:...>>>` и внутренние имена пакетов остаются нетронутыми.

## Testing Strategy

- **Unit-тесты**: обязательны для каждой задачи
- **Захардкоженные пути**: 37 тестовых файлов содержат «ralphex»; часть — в путях конфига и
  progress-каталогов. После каждой задачи переименования прогонять полный `go test ./...`,
  а не только затронутый пакет — пути протекают между пакетами
- **E2E**: playwright-тесты дашборда (`e2e/`) остаются. `e2e/testdata/test-plan.md` содержит
  «ralphex» — проверить, значимо ли это для теста, и обновить при необходимости
- **Безопасность тестов**: никаких обращений к `~/.config/ralphex/` и `~/.config/loopai/`.
  Все файловые операции — через `t.TempDir()`. После прогона сверить, что реальные каталоги
  конфига не изменились

## Technical Details

### Что переименовано, а что нет

| Слой | Решение | Причина |
|---|---|---|
| Имя бинаря, `cmd/` | `loopai` | видит пользователь |
| Каталоги конфига и данных | `~/.config/loopai/`, `.loopai/` | иначе форк делит конфиг с апстримным ralphex |
| Пользовательские строки | `loopai` | видит пользователь |
| `module` в `go.mod` | **остаётся** `github.com/umputun/ralphex` | смена ломает мерж апстрима в 78 файлах |
| Сигналы `<<<RALPHEX:...>>>` | **остаются** | 198 вхождений в коде и промптах; ломает старые progress-логи и кастомные промпты |
| Имена Go-пакетов | **остаются** | внутреннее, пользователю не видно, смена мешает мержу |

### Порядок задач

Удаление (1-3) идёт до переименования (4-6) сознательно: каждый удалённый файл — это файл, в котором
не придётся ничего переименовывать. Обратный порядок означал бы переименование в 5700 строках
Docker-обёртки, которые тут же пойдут в корзину.

Задача 5 (каталоги) отделена от задачи 6 (строки), потому что первая может сломать тесты по всему
репозиторию через захардкоженные пути, а вторая почти безопасна. Смешивать их — значит разбираться
с двумя разными типами падений одновременно.

### Побочные эффекты чистого разрыва

- Старые progress-логи в `.ralphex/progress/` перестанут быть видны дашборду. Файлы остаются на диске,
  но новый бинарь пишет в `.loopai/progress/`.
- В проектах, где уже есть `.ralphex/` с локальным конфигом, `loopai` его не увидит и применит
  глобальные настройки. Перенос — вручную, одним `mv`.
- Ключ статуса в cmux меняется с `ralphex` на `loopai`. Если в момент обновления в сайдбаре висела
  пилюля со старым ключом, снять её придётся вручную: `cmux clear-status ralphex`.

## Post-Completion

*Требует человека, автоматизации не поддаётся*

**Установка и перенос:**
- Собрать и поставить новый бинарь: `make build && cp .bin/loopai ~/.local/bin/loopai`
- Удалить старый бинарь `ralphex` из `~/.local/bin/`, если он там остался от предыдущей сборки
- Перенести личные правки конфига: `cp -r ~/.config/ralphex ~/.config/loopai`, затем сверить, что
  кастомные промпты и агенты на месте
- В проектах с локальным конфигом: `mv .ralphex .loopai`

**Проверка вживую:**
- Прогнать `loopai` на реальном плане и убедиться, что баннер, пути логов и статус в cmux
  показывают loopai
- Проверить `loopai --init` в чистом проекте — должен создаться `.loopai/`
- Проверить дашборд `loopai --serve` — читает ли он progress из нового каталога

**Синхронизация с апстримом:**
- Проверить, что `git merge upstream/master` проходит без конфликтов по строкам импорта.
  Это главный критерий успеха выбранной глубины ребрендинга; если конфликты всё же массовые —
  вернуться и разобраться, что именно их вызывает
